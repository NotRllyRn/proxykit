## Decision

Bifrost has substantial **implemented AI gateway capabilities**, plus genuine Go interfaces for hooks, account lookup, key selection, MCP tools, and observability. It is a credible **Go SDK/custom-host foundation**. It is **not established that one stock-server dynamically loaded plugin can implement the full Codex Broker or durable recall design** through its public plugin contract. Key distinctions:

- `BifrostConfig.Account`, `KeySelector`, `KeyPoolFilter`, and `RegisterMCPTool` are SDK/host APIs. The `.so` plugin loader does not pass a Bifrost instance, router, account-provider registry, store, or jobs service to `Init(config any)`.
- HTTP pre-auth credential translation and committed routing/key-pin hooks exist. They can augment host authentication and selection; that does not make them a full replaceable inbound-auth/account lifecycle provider.
- Gateway-owned MCP tool execution exists for **non-streaming Chat/Responses**. Mixed tool calls stop at pending client tools, but synthesized gateway-result summaries are lossy for repeated calls to one tool. No streaming autonomous MCP loop was found; the source and documentation agree on that limitation.
- Independent request/response and attempt observability is feasible, including async `Inject` traces. Default export is **best effort**, with bounded concurrency and dropped traces under saturation; it is not a durable exactly-once ledger.
- Request rewriting is supported. Durable transcript archival, transactional archive-before-removal, session revision reconciliation, and restart-safe replay are **plugin-owned work not supplied by the reviewed plugin interfaces**. Logging/cache persistence and provider compaction endpoints are not equivalent contracts.

## 1. Public extension surface and trust boundary

[Plugin contract](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/plugin.go#L278): `BasePlugin.GetName/Cleanup`; HTTP hooks `HTTPTransportPreAuthHook`, `HTTPTransportPreHook`, `HTTPTransportPostHook`, `HTTPTransportResponseHeadersHook`, `HTTPTransportStreamChunkHook`; LLM `PreRequestHook`, `PreLLMHook`, `PostLLMHook`; MCP `PreMCPHook/PostMCPHook`, optional connection hooks; A2A hooks; observability `Inject`. `RelayPlugin` is explicitly described as an internal hook surface, not a user-configured plugin role. Optional config marshalling/redaction is separate.

[Native loader](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/framework/plugins/soloader.go#L67) calls optional exported `Init(config any) error`, requires exported `GetName` and `Cleanup`, and looks up optional named hook symbols. This is trusted in-process native code loaded with Go `plugin.Open`, not a security sandbox. No manifest-enforced filesystem/network capabilities, scoped database, secret-handle-only access, route registration, tool registration, or account-provider registration is passed through this loader. A native plugin can of course open files/network connections/start goroutines itself; those are plugin-owned capabilities and failure/lifecycle obligations, not host guarantees. Serializable HTTP types and WASM schema files do not by themselves establish an available sandboxed loader; this audit validated the native loader only.

The [SDK config](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/bifrost.go#L20) additionally exposes `Account`, `KeySelector`, `KeyPoolFilter`, `KVStore`, `SessionAffinity`, MCP/OAuth backends, and injected plugins. This is a broader integration surface than stock dynamic-plugin registration. The [stock server initialization](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/server/server.go#L3622) creates `lib.NewBaseAccount(s.Config)` and passes it to `bifrost.Init`; it does not obtain an Account/KeySelector from generic plugin `Init`.

## 2. Codex Broker capability mapping

### Inbound auth

`HTTPTransportPreAuthHook` can mutate headers/query/body before inference authentication or return an immediate response/error. This is a real seam for translating a trusted caller identity into host credentials. Method/path changes are rejected with HTTP 409 because routing already happened. Post-auth `HTTPTransportPreHook` can inspect the resolved identity, mutate a request, or reject it. The [middleware installation](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/server/server.go#L3814) attaches these phases to registered inference routes.

Important nuance: the [OSS inference auth middleware](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/middlewares.go#L1778) deliberately passes inference through and delegates authoritative virtual-key validation to the governance plugin. Its comment states governance is loaded unconditionally and cannot be disabled in OSS. Dashboard/API authentication is separate. Thus pre-auth translation is **not evidence that a custom plugin can replace all governance validation and administrative auth**. A short circuit can bypass downstream work by answering the request itself, but implementing an entire proxy in that callback would not count as host-supplied broker forwarding.

Actual tests selected: `TestTransportPreAuthInterceptorMiddleware_HeaderVisibleToNext`, `BodyIsModifiable`, `ShortCircuitResponse`, `PluginError`, `PathMutationRejected`, and `NoPlugins`; final execution status is in `bifrost-test-summary.md`.

### Upstream account/key selection and refresh

[Account](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/account.go#L1403) defines `GetConfiguredProviders()`, `GetKeysForProvider(context.Context, ModelProvider)`, and `GetConfigForProvider(ModelProvider)`. A custom SDK host can implement dynamic per-caller account lookup and refresh before returning keys. It owns storage, refresh coordination, retries, and account CRUD. `KeySelector(ctx, keys, provider, model)` chooses a `Key`; `KeyPoolFilter` vetoes candidates. The normal implementation defaults to weighted-random selection. Key filtering, rotation, retries and session affinity remain core behaviors, not arbitrary extension replacement.

A hook can use `PreRequestHook` to change route/model/fallbacks and the nonreserved `BifrostContextKeyRoutingPinnedAPIKeyID`; core [commits that pin](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L9881) after restricted writes are unblocked. Direct writes to reserved context keys can be silently ignored. Tested `TestRunPreRequestHooks_CommitsRoutingPinnedKey` proves pin commitment and precedence over a caller pin. [Selection code](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L11330) applies skip-key conditions, account retrieval and eligible-key filtering. Do not equate arbitrary context mutation with a supported credential-injection provider role.

[Key fields](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/account.go#L137) include `ID`, `Name`, `Value SecretVar`, `Models`, `BlacklistedModels`, `Weight`, `Enabled`, `Description`, aliases and provider-specific configs. `Name` and `Description` provide labels; no generic account-label/tenant-ACL extension schema was identified there.

Built-in [OAuthKeyConfig](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/account.go#L1274) supports `client_credentials` and `jwt_bearer` token mint/cache/refresh for compatible providers. MCP's OAuth refresh interfaces address MCP credentials. Neither establishes ChatGPT user refresh-token rotation/enrollment for a broker pool. A custom Account or plugin can implement its own refresh network/storage logic; no general plugin refresh-provider registration was found in the audited contract/loader.

### Enrollment and account management endpoints

Implemented provider/key CRUD ([routes](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/providers.go#L250)):

- `GET/POST /api/providers`, `GET/PUT/DELETE /api/providers/{provider}`.
- `GET/POST /api/providers/{provider}/keys`, `GET/PUT/DELETE /api/providers/{provider}/keys/{key_id}`.
- `POST /api/providers/{provider}/refresh-models`, `POST /api/providers/{provider}/keys/{key_id}/refresh-models` refresh model discovery, not account credentials.

Implemented virtual-key control plane ([routes](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/governance.go#L1820)): CRUD `/api/governance/virtual-keys`, rotation, teams, customers, budget/rate limits, and provider/model governance. [Virtual-key provider config](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/framework/configstore/tables/virtualkey.go#L27) has `AllowedModels`, `BlacklistedModels`, `AllowAllKeys`, selected `Keys`, budget/rate-limit associations. Empty allowed-model/selected-key lists deny by default unless explicit unrestricted settings apply. These are built-in ACL/account-pool primitives, not general plugin-defined CRUD/ACL registration. Enterprise administrative RBAC implementation was not audited.

There **is** built-in device enrollment for **GitHub Copilot**, not a generic public enrollment extension: [handler](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/githubcopilotsignin.go#L44), `POST /api/providers/{provider}/sign-in` and `/sign-in/poll`, registered with management middlewares. It returns credentials to the key form for saving. MCP has [OAuth callback/status/revoke](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/mcpoauth2.go#L44), including `/api/oauth/config/{id}/status`; that is a different credential domain. Do not report either as public ChatGPT broker enrollment start/poll.

No dynamic-plugin arbitrary-route registration symbol was found in `plugin.go`, `PluginLoader`, `soloader.go`, or stock server initialization. [Unknown routes return 404](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/server/server.go#L3225). Adding public `/enroll/start` and `/enroll/poll` is established for a custom Go host/router, not established for a drop-in plugin on the existing server. Intercepting an existing inference route or running a plugin-owned second listener is possible native-code work, but changes the integration/operational contract.

### Actual Codex transport support

A built-in [ChatGPT passthrough router](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/integrations/passthrough.go#L104) forwards to `https://chatgpt.com`, explicitly restricted to `GET /chatgpt_passthrough/backend-api/codex/models` and `POST /chatgpt_passthrough/backend-api/codex/responses`. It supports caller sign-in-token passthrough and treats the Responses path as streaming even without the body stream flag. This is substantial client compatibility infrastructure, but **caller credential passthrough is not broker-owned OAuth account selection, refresh, or enrollment**. No live ChatGPT/Codex validation was performed.

## 3. Independent request/response/attempt usage recorder

Yes, there are useful public hooks. `PreLLMHook` sees typed requests; `PostLLMHook` sees response/errors and streaming response chunks; HTTP hooks see transport payloads within their documented buffering constraints; `ObservabilityPlugin.Inject(context.Context, *Trace)` receives completed traces asynchronously. Data retention requires copies: pooled objects/trace pointers must not outlive callback ownership.

Do not treat one pre/post pair as one upstream attempt. PreRequest runs once per top-level request, PreLLM reruns on fallbacks, while core's [retry executor](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L7271) owns retries/key rotation within an attempt pipeline. It creates model-call and `retry.attempt.N` spans ([source](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L7594)) and populates response/usage attributes before ordinary downstream response hooks ([source](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L7774)). `Inject`/trace spans are the relevant seam for independent attempt records; failures with no provider usage do not establish zero billing.

MCP continuations call core's request method again, obtain new request IDs when configured, retain the original agent request ID, and [accumulate usage](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/mcp/agent.go#L153). Summing both each call and the final accumulated agent result would double count. Proper recording must distinguish wire delivery, logical agent turn, provider attempt, and accumulated presentation values. The added usage probe observed initial 12 tokens plus a 23-token continuation delivered as 35, with gateway call/result IDs paired in the continuation input.

[Tracer export](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/framework/tracing/tracer.go#L1380) snapshots spans, fans out per connector, skips saturated connectors and counts drops. [Plugin limits](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/plugin.go#L527) configure `semaphore_size` and `inject_timeout`; defaults are 10,000 and 5 seconds. Timeouts are cooperative context cancellation; a plugin ignoring context still holds its goroutine and slot until it returns. Traces are not durably queued by this mechanism. Built-in logging has its own persistence implementation; that does not promise exactly-once storage for arbitrary exporters.

Tested local exhausted-fallback scenario records each attempt for both streaming and non-streaming. This does **not** validate every provider's usage parser, every retry's billed usage, or durable independent ingestion after crash. Exact test results and remaining scope are in the test summary.

## 4. Durable context archive, compaction and restart replay

**Partial mechanism; end-to-end requirement not established.** A plugin can transform typed input in PreRequest/PreLLM, inject instructions/tool schemas, observe outputs, and use its own database. Native plugin code can implement persistence, migrations, locks, embeddings/search, extraction jobs, and reconciling repeated client histories. None of those semantics follows automatically from a request hook.

The reviewed public plugin contract has no host archive transaction, context-revision/session ownership API, transcript append/CAS, archive-before-removal commit, or replay-reconciliation service. [KVStore](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/kvstore.go#L5) is an injected internal minimal `Get/SetWithTTL/SetNXWithTTL/Delete` interface for clustering/stickiness, not a durable transcript service handed to every plugin. Its presence does not establish restart durability or atomic archive/working-context updates.

MCP agent history/results are local variables in `executeAgent`; the loop does not archive its continuation state. Mixed results are synthesized into final output; no persisted map reconciles the client's next full-history replay to hidden gateway history. Existing logging, semantic-cache replay and provider `/responses/compact` support are different features. Bounded negative search included `core/schemas/plugin*`, `framework/plugins`, agent/adaptor code, and archive/compaction/replay references under `plugins`. This supports “not supplied by the reviewed extension seams,” not “no storage or compaction code exists anywhere.”

No restart/archive probe was claimed: there was no host archive/replay API to drive. A dummy plugin writing its own SQLite/file would only prove the plugin's implementation. Tenant isolation, concurrent revision correctness, provider-held `previous_response_id`, signed reasoning fidelity through compaction, archive failure, and restart recovery remain unvalidated for a proposed recall plugin.

## 5. Gateway-owned tools, mixed tools, streaming

The SDK has [RegisterMCPTool](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L4612), accepting name, description, `func(args any) (string, error)` and schema. This callback does not accept a context parameter. External MCP servers and in-process server factories are other host-configured sources. The dynamic-plugin loader does not supply the client/manager for registering tools during Init; an extension can instead be paired with an operator-configured MCP server. Model schema injection alone does not cause arbitrary function tools to become host-executable.

[Agent loop](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/mcp/agent.go#L140): classify tool calls using MCP client config `ToolsToExecute`/`ToolsToAutoExecute`; unknown caller-provided tools are non-auto-executable. Auto tools run first. If any client tool remains, stop and return pending calls immediately without another LLM request. Tested with a synthetic gateway call plus `client_tool`: one gateway execution, zero continuation calls, pending ID retained as `client-id`.

However, mixed handoff is not lossless native tool replay. [Chat result synthesis](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/mcp/agentadaptors.go#L348) creates text `The Output from allowed tools calls is - {...}` and retains only pending tool calls, with `finish_reason: stop`. Results are keyed by **tool name**, not call ID. The local duplicate-tool probe proves two `lookup` calls become only the second result in this summary. Parallel completion order means the surviving value can depend on execution timing. A second local probe confirms the same loss on Responses; Responses synthesis uses the same name-keyed summary pattern ([source](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/mcp/agentadaptors.go#L590)). Media summary placeholders also are not lossless archival. Pending call IDs being preserved is a narrower success than full native-tool history fidelity or compatibility with every client.

[Non-streaming Chat entry](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L1063) and Responses equivalent invoke CheckAndExecuteAgent after receiving a complete response. The streaming sibling does not invoke this loop. [Documentation](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/docs/mcp/agent-mode.mdx#L17) explicitly says `chat_stream`/`responses_stream` are unsupported for Agent Mode. Stream chunk hooks permit interception; they are **not** a host-owned streaming mixed-tool continuation engine. A plugin could short-circuit with its own stream and implement the loop, but would own buffering, continuation, cancellation, usage and replay correctness.

Real MCP tool execution has a [timeout context](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/mcp/toolmanager.go#L897), using per-server override or the global default of 30 seconds and the caller's earlier deadline. This is a meaningful host limit beyond the callback-only loop probe. Depth is bounded by `maxAgentDepth`; tool fan-out is not bounded within that loop: one goroutine per auto call and `WaitGroup.Wait()`. The audit held 64 mock callbacks behind a barrier and observed all 64 enter before releasing any. An already-canceled context still dispatched a tool and a continuation callback; cancellation is propagated but the loop itself does not gate those calls. Real downstream executors may honor it; the probe deliberately establishes the loop's boundary, not a claim that every real provider ignores cancellation. No global elapsed/spend/output budget was established for this loop beyond caller/dependent service controls.

## 6. Failure, ordering, concurrency and stream commitment

- **Core errors fail open:** [RunLLMPreHooks](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/bifrost.go#L9818) logs/appends returned Go errors and continues. The probe verifies a failed policy's model mutation survives and a later observer executes. `PreRequestHook` similarly cannot deny through an error return. “Thrown errors” in JS terminology maps here to returned Go errors; Go panic is a separate case, not tested by these probes.
- **Explicit denials:** return `LLMPluginShortCircuit{Error: ...}`; set `BifrostError.AllowFallbacks=false` when denial must not route elsewhere. Probe verifies later pre-hooks do not execute and only the entered pre-hook receives its paired post-hook. Post-hooks can also recover from errors; ordering matters for protection. No operator-level mandatory-role fail-closed override was identified in generic PluginConfig.
- **HTTP differs:** pre-auth/pre/post returned errors reject rather than behaving like core LLM errors. Header hooks run before commitment and cannot mutate framing headers. Header-hook errors retain mutations already made, warn, and stop remaining header hooks. This is not transactional rollback.
- **Streaming:** [pluginChunkInterceptor](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/lib/config.go#L8540) executes in reverse order. `(nil,nil)` drops a chunk; `(chunk,error)` stops remaining hooks for this chunk and the handler warns and sends that chunk; `(nil,error)` emits an error, cancels and drains the upstream stream ([handler](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/handlers/inference.go#L2527)). Already delivered bytes cannot be undone. There is no automatic semantic reconciliation of arbitrary edits with final completed objects.
- **Composition:** pre-hooks are registration order, paired post-hooks reverse order. [SortAndRebuildPlugins](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/transports/bifrost-http/lib/config.go#L9075) groups pre-built-in / built-in / post-built-in, numeric Order and stable ties. No dependency DAG/cycle validation contract was found. Live config swapping does not establish durable session ownership or safety for plugin-owned goroutines during reload.
- **Resource bounds:** [provider defaults](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/core/schemas/provider.go#L20) include provider concurrency 1000, queue buffer 5000, stream buffer 256; network defaults/request deadlines and idle timeouts are separate. `DropExcessRequests` controls full queues. These do not bound arbitrary hook CPU/wall time or agent tool fan-out. Direct synchronous hook calls carry a context, without an independent per-hook forced preemption mechanism in the reviewed runners.

## 7. Storage, jobs, arbitrary routes and protocols

Bifrost has real framework storage and background jobs; absence of a dynamic-plugin service injection API must not be reported as absence of all jobs. [Sidekiq Runner](https://github.com/maximhq/bifrost/blob/6e640279b36337820f2088fb85f6e78f339063c3/framework/sidekiq/sidekiq.go#L17) uses a store with atomic job claims, heartbeats, progress/checkpoints, completion/failure, cancellation, and partitioned claims. It has `Register(kind, HandlerFunc)`, default concurrency 4, 15-minute stale reclaim, and five reclaim attempts. It can support plugin-like work in a custom host. The native loader does not inject this runner or the ConfigStore; plugin authors must arrange integration and idempotency themselves. No durable-job runtime test was run here.

The gateway supports many typed AI operations, passthrough integrations, MCP, A2A, SSE, and WebSocket/Realtime routes. This is not a generic arbitrary-protocol plugin ABI. SDK users can build their own HTTP server/middleware/router. Custom provider config can reuse supported base-provider protocols and override URLs; a fundamentally new provider wire protocol requires implementing/wiring host Provider behavior rather than exporting an ordinary hook. HTTP hooks only run on routes where the host installed them; pre-auth path mutation is rejected. Built-in passthrough prefixes provide raw forwarding for their supported methods/paths; they do not establish arbitrary route registration by dynamic plugins. No WebSocket wire probe was run in this audit.

## 8. Coverage boundary and acceptance implications

Answered by source plus local execution: non-stream mixed tool stopping/IDs, duplicate summary result loss, loop cancellation boundary and tool fan-out, core error versus explicit-denial behavior and hook order, routing pin semantics, selected mock streaming/fallback/attempt scenarios. HTTP hook, header commitment, exporter saturation/timeout, and stream-interceptor return-semantics tests also passed; see the test summary and raw logs.

Answered statically: SDK Account/KeySelector seam versus dynamic-plugin loader, built-in account/virtual-key CRUD, OAuth grant domains, device sign-in domain, no general route registration among reviewed hook symbols, non-stream-only MCP loop, queue and exporter bounds, Sidekiq service versus plugin injection.

Not established: complete Broker plugin implementation, public ChatGPT enrollment/refresh/account ACLs through stock dynamic hooks, restart-safe archive/replay, concurrent context revisions, independent durable usage ledger under crash/saturation, streaming mixed gateway/client tool orchestration, actual Codex client compatibility, live provider accounting and cancellation, enterprise RBAC, WASM runtime/security, arbitrary-protocol plugins. No marketing overhead/performance claims were benchmarked or adopted.

For ProxyKit, useful architectural precedents are explicit routing before per-attempt hooks, a real account/key selector seam, early HTTP auth translation, pre-commit header hooks, separate async trace consumers with limits/drop counters, and a host non-stream MCP loop. The missing or weaker parts are exactly the proposed host roles: plugin-accessible account/enrollment/route services, required-policy failure contracts, durable context transactions, a bounded streaming mixed-tool loop, and durable original-usage capture independent of presentation rewriting.
