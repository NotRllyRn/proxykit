## Correction to the earlier interpretation

The original checklist scored whether the gateway supplied the subsystem. The intended question is whether an extension can supply it using its own application and the gateway's extension interfaces. Under that model, absence of a gateway database, dashboard router, enrollment listener or job scheduler is not a blocker. All three audited trusted runtimes allow ordinary application code to use the filesystem, network, workers and companion services, subject to deployment permissions. This is source-supported feasibility, not a tested turnkey package deployment.

A useful deployment is: browser → extension enrollment/dashboard listener → extension database/workers; model client → gateway → extension request/account/response adapter → upstream provider. The two extension parts can share a database or use authenticated local IPC/HTTP. They can run in one process where suitable or as separately supervised processes. Being on the same machine is not an integration mechanism by itself: the adapter still needs the right gateway hooks.

## What the enrollment terms meant

- **Public enrollment POST:** a browser submits a state-changing enrollment request, for example `POST /start`. POST is an HTTP method, not a special gateway permission. The extension's own web server can serve it.
- **Private service auth:** if a public-facing enrollment component calls a private broker component, that private API verifies the service's identity and limits it to enrollment operations. It is separate from user model-routing credentials and dashboard-admin credentials. The extension can implement both sides; if there is no service boundary, no private HTTP endpoint is required.
- **Isolated listener:** a separate network address/port can expose only enrollment routes. A port in the same process does not isolate memory or credentials. If that stronger boundary is wanted, run the public component separately with narrower credentials. The gateway need not supply the listener or process manager.
- **Atomic activation, labels and notification outbox:** commit the account becoming eligible, its label assignments and a pending notification record in one database transaction. A worker sends/retries the notification later. This can belong entirely to the extension. The remaining boundary is when the gateway has a separate account store: the extension must reconcile publication and ensure account selection respects the committed eligibility state. Two databases do not become atomic merely because they run on one server.

## Updated interpretation and recommendation

**All three become more viable. CLIProxyAPI gains the most for a Broker-centered application.** Its auth acquisition/refresh, scheduler, executor and nested model-call APIs pair naturally with a self-hosted broker application. Its missing general database/jobs/public-POST APIs are no longer reasons to reject it. A tool-loop implementation can also live in an extension; the existing stream/model bridges are useful building blocks, though full mixed-tool/replay correctness remains unproven.

**CCR remains the closest TypeScript option**, with the widest direct route/protocol/transform roles and an existing streaming internal-tool path. Its own-service capability is especially natural in Node. If the extension uses that built-in loop, its tested hook bypass, replay and mixed-call limitations still apply. Owning the loop instead is a possible integration choice, not evidence those limitations are fixed.

**Bifrost improves for dashboards, enrollment services, storage and jobs**, but its stock plugin-to-account/provider integration remains narrower than its SDK. A standalone service does not automatically obtain the SDK Account/KeySelector interfaces. A custom host or control-plane integration may still be necessary; its built-in autonomous MCP loop remains nonstreaming.

**Revised recommendation:** do not build a new proxy solely because these projects lack extension-owned web servers, storage or jobs. For a Broker-first application, CLIProxyAPI is now a first-choice candidate to evaluate alongside CCR for TypeScript ergonomics. The remaining deciding question is whether the adapter can control every needed request/attempt/stream/tool boundary. Existing evidence does not establish that all three can implement every desired feature together unchanged, but it also does not justify treating missing host-owned subsystems as blockers.

## Legend and evidence

- **Supported:** relevant gateway/runtime mechanism exists. It does not mean the feature application is already built.
- **Extension-owned:** ordinary extension application code can supply it; no special host API is necessary. These are feasibility judgments, not new runtime passes.
- **Integration needed:** own services are allowed, but access/control of gateway-owned work still matters.
- **Host gap:** the requested guarantee depends on host behavior that an external service alone cannot fix.
- **Unverified:** insufficient evidence. **Optional:** not required under the trusted-extension model.

Each row includes the prior status in the JSON/HTML and retains its original ID. S = inspected source, I = feasibility inference; references to prior T retain the earlier test scope. Do not combine these statuses into a percentage score: an extension-owned database and a missing fail-closed request boundary have very different consequences.

## Which issues remain at the gateway boundary?

1. **Missing or late hooks:** an extension's dashboard cannot observe private loop output if the host never emits it to that extension, or restore a tool result already discarded upstream of its callback. Own orchestration can avoid some paths but needs sufficient entry/stream control.
2. **Failures outside extension control:** explicit denial can work while an unexpected plugin error/unload still makes the gateway continue. Putting policy logic in another process does not fix a fail-open adapter.
3. **Cancellation and commitment:** the extension can cancel its own jobs, but the gateway must expose disconnection/deadline signals and let it stop upstream work. Bytes already delivered cannot be retracted.
4. **Account activation versus host eligibility:** own enrollment is easy to separate; having retries/fallbacks choose only allowed, committed accounts is an integration contract.
5. **Loss before telemetry delivery:** own durable storage protects received records. It cannot recover events the gateway drops before the callback, or distinguish unknown usage from zero when that information has already been erased.
6. **Independent extension composition:** one application can coordinate all its components. Separately authored plugins still need compatible stages, ownership and ordering; a common port or database does not establish that automatically.

Tool loops, replay databases and revision managers may all be extension-owned under the clarified model. The gateway only needs the corresponding visibility/control/cancellation/forwarding primitives if it does not supply the loop. There is no requirement here to force all extensions through a host-owned agent framework.
